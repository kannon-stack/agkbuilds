# Hermes Agent: LLM providers and running against a LOCAL inference backend (Ollama / llama.cpp / vLLM / SGLang / LM Studio)

Research date: 2026-11-08. Docs read are the "current" (main-branch) Docusaurus build at hermes-agent.nousresearch.com plus raw source on `main` of github.com/NousResearch/hermes-agent. Version context: newest git tag is `v0.23.0` (with daily `v0.23.0+canary.2026110xT...` tags) ([tags](https://github.com/NousResearch/hermes-agent/tags)); PyPI `hermes-agent` shows only up to `0.19.0` ([PyPI](https://pypi.org/project/hermes-agent/)); GitHub issue reports cite v0.13.0 (May 2026), v0.16.0 (Jun), v0.18.2 (Jul) and v0.20.3 (Sep) ([#25629](https://github.com/NousResearch/hermes-agent/issues/25629), [#53347](https://github.com/NousResearch/hermes-agent/issues/53347)).

## 1. Which providers are supported, how they are selected, and which API style is used

### Takeaway
Hermes supports ~45 built-in providers plus a first-class `custom` provider for any server that implements `/v1/chat/completions`; selection lives in `~/.hermes/config.yaml` under `model:` (`provider`, `default`, `base_url`, `api_key`/`key_env`), set interactively with `hermes model` (setup wizard, outside a session) or switched in-session with `/model`. The wire format for local servers is OpenAI Chat Completions with native `tools` / `tool_choice: "auto"`; text-embedded tool calls are only partially rescued by an "auto-repair" path, so the server must emit structured `tool_calls`.

### Cited Findings
- Provider table includes Nous Portal (OAuth), OpenAI Codex (ChatGPT OAuth), Anthropic (OAuth/API key), OpenRouter (`OPENROUTER_API_KEY`), Fireworks, NovitaAI, z.ai/GLM, Kimi, MiniMax, xAI, Qwen/DashScope, DeepSeek, Hugging Face, Gemini, Vertex, OpenAI API direct (`provider: openai-api`, `OPENAI_API_KEY`, optional `OPENAI_BASE_URL`), Azure Foundry, AWS Bedrock, NVIDIA, Ollama Cloud (`provider: ollama-cloud`), LM Studio (`provider: lmstudio`, optional `LM_API_KEY`) and "Custom Endpoint" (saved in `config.yaml`) — [Providers](https://hermes-agent.nousresearch.com/docs/integrations/providers#inference-providers)
- "Hermes Agent works with **any OpenAI-compatible API endpoint**. If a server implements `/v1/chat/completions`, you can point Hermes at it." — [Providers: Custom & Self-Hosted](https://hermes-agent.nousresearch.com/docs/integrations/providers#custom--self-hosted-llm-providers)
- Manual config form: `model: {default: your-model-name, provider: custom, base_url: http://localhost:8000/v1, api_key: your-key-or-leave-empty-for-local}` with optional `key_env: MY_PROVIDER_API_KEY`; `default:` and `model:` are interchangeable key names for the model ID — [Providers: General Setup](https://hermes-agent.nousresearch.com/docs/integrations/providers#general-setup)
- Env-var changes: `LLM_MODEL` in `.env` is **removed**; `config.yaml` is the single source of truth. `OPENAI_BASE_URL` is still honored **only** for the `openai-api` provider; stale `.env` entries are auto-cleared on next `hermes setup`/migration — [Providers: General Setup](https://hermes-agent.nousresearch.com/docs/integrations/providers#general-setup)
- `hermes model` = full setup wizard (run in terminal, outside a session; adds providers, OAuth, keys, endpoints). `/model` = in-session switch among already-configured providers only (e.g. `/model custom:qwen-2.5`, bare `/model custom` auto-selects if the endpoint's `/models` lists exactly one model, `/model custom:local:qwen-2.5` for named providers) — [Providers: Switching Models](https://hermes-agent.nousresearch.com/docs/integrations/providers#switching-models-with-model)
- `provider: custom` "is a first-class provider, not an alias for anything else"; FAQ example uses API key `ollama` and model `qwen3.5:27b` — [FAQ](https://hermes-agent.nousresearch.com/docs/reference/faq#can-i-use-it-offline--with-local-models)
- In source, the `custom` provider profile has aliases `ollama`, `local`, `vllm`, `llamacpp`, `llama.cpp`, `llama-cpp` — [plugins/model-providers/custom/__init__.py](https://github.com/NousResearch/hermes-agent/blob/main/plugins/model-providers/custom/__init__.py)
- `hermes chat --provider ollama` (or `vllm`) with no endpoint configured stops with "provider 'ollama' has no endpoint configured" — Hermes "refuses to send the request rather than fall back to OpenRouter with a cloud key"; fix with `providers: {ollama: {base_url: "http://localhost:11434/v1"}}` — [Ollama guide: Troubleshooting](https://hermes-agent.nousresearch.com/docs/guides/local-ollama-setup#provider-ollama-has-no-endpoint-configured)
- Named custom providers live under a top-level `providers:` dict. Keys: `api` (aliases `base_url`/`url`), `name`, `key_env` / inline `api_key` / `key_cmd`, `transport` (`chat_completions` / `anthropic_messages` / `codex_responses`), `default_model`, `models` (per-model `context_length`, `supports_vision`, `timeout_seconds`…), `context_length`, `discover_models`, `extra_body`, `extra_headers`, `ssl_ca_cert`/`ssl_verify`, `catalog_provider`, `enabled: false`. If `api_key` is omitted, "Hermes uses `no-key-required` for keyless local servers" — [Providers: Named Custom Providers](https://hermes-agent.nousresearch.com/docs/integrations/providers#named-custom-providers)
- Legacy top-level `custom_providers:` list still works and is auto-migrated by `hermes update` to the `providers:` dict (config v12); legacy `model` → `default_model`, legacy `api_mode` → `transport` — [Providers: Named Custom Providers](https://hermes-agent.nousresearch.com/docs/integrations/providers#named-custom-providers)
- The Custom Endpoint wizard now prompts for API mode explicitly and persists it as `transport`; URL-based auto-detection (e.g. `/anthropic` path → `anthropic_messages`) is the fallback — [Providers](https://hermes-agent.nousresearch.com/docs/integrations/providers#named-custom-providers)
- vLLM section: `--enable-auto-tool-choice` is "Required for `tool_choice: "auto"` (the default in Hermes)"; without parser flags "the model will output tool calls as text" — [Providers: vLLM](https://hermes-agent.nousresearch.com/docs/integrations/providers#vllm--high-performance-gpu-inference)
- "Hermes has auto-repair — it detects malformed tool calls and attempts to fix them automatically", but raw JSON like `{"name": "web_search", ...}` printed as a reply is "usually the server" not having tool calling enabled/parsed — [Ollama guide](https://hermes-agent.nousresearch.com/docs/guides/local-ollama-setup#model-doesnt-follow-tool-calls)
- Reasoning: when no effort is configured, `chat_completions` requests to custom endpoints carry `reasoning_effort: medium`; models marked non-reasoning and "Ollama models without the `thinking` capability" keep the field off — [Providers](https://hermes-agent.nousresearch.com/docs/integrations/providers#named-custom-providers). Source: effort `none` sends top-level `reasoning_effort: "none"` plus `think: false` only on URLs that look like Ollama (port 11434 or an `ollama` host label) — [custom provider source](https://github.com/NousResearch/hermes-agent/blob/main/plugins/model-providers/custom/__init__.py)
- `extra_body` on a `providers.<name>` entry is merged into every chat-completions request (e.g. `chat_template_kwargs: {enable_thinking: false}` for vLLM Qwen); it is re-derived on `/model` switches — [Providers](https://hermes-agent.nousresearch.com/docs/integrations/providers#named-custom-providers)
- `model.streaming: false` forces non-streaming for the whole session (escape hatch for servers whose streaming tool-call path is broken); Hermes also auto-switches to non-streaming if a server reports streaming unsupported — [Configuration: Disabling API streaming](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#disabling-api-streaming)
- Hermes no longer reads `model.max_tokens`, `HERMES_MAX_TOKENS` or `model_overrides.*.*.max_output_tokens`; custom endpoints get no automatic output cap (server defaults apply); a repetition loop is cut after ~130,000 chars with a "Repetition Detected" notice — [Providers: Context Length Detection](https://hermes-agent.nousresearch.com/docs/integrations/providers#context-length-detection)
- Fallback chain: top-level `fallback_providers:` list (legacy `fallback_model:` dict still accepted); one-shot per session; `custom` and `lmstudio` are valid entries — [Providers: Fallback Providers](https://hermes-agent.nousresearch.com/docs/integrations/providers#fallback-providers)

### Inferences
- For a fully local setup the minimal, unambiguous config is `model.provider: custom` + `model.base_url: http://127.0.0.1:<port>/v1` + `model.default: <exact id from GET /v1/models>` + an explicit `model.context_length`. Do not rely on `OPENAI_BASE_URL` (ignored except for `openai-api`).
- Leaving `api_key` empty is fine for keyless local servers (Hermes substitutes `no-key-required`); if a server like vLLM was started with `--api-key`, set `api_key` or `key_env`.
- Hermes is a native-tool-calling agent: the reliability of tool use is decided by the server's chat template / tool-call parser, not by Hermes prompting. Validate with a curl request that includes `tools` and check that `choices[0].message.tool_calls` is populated before blaming Hermes.
- Do not configure `fallback_providers` with a cloud provider if the goal is "never call a paid API".

### Gaps
- No doc states the exact count/size of tool schemas sent per request for the default toolset (see Q3/Q6 for conflicting numbers).
- Whether Hermes ever uses `tool_choice: "required"` or parallel tool calls on custom endpoints was not verified in source.

## 2. What the docs say about specific local backends (URLs, keys, server flags for tool calling)

### Takeaway
Every local backend is configured as a custom endpoint (LM Studio also has its own `lmstudio` provider; a managed llama.cpp runtime exposes `provider: llamacpp`). Default URLs: Ollama `http://localhost:11434/v1`, llama-server `http://localhost:8080/v1`, vLLM `http://localhost:8000/v1`, SGLang `http://localhost:30000/v1`, LM Studio `http://localhost:1234/v1`. Tool calling needs server-side switches: llama.cpp `--jinja`; vLLM `--enable-auto-tool-choice --tool-call-parser <name>`; SGLang `--tool-call-parser <name>`; Ollama is on by default but needs a tool-capable model; LM Studio ≥0.3.6.

### Cited Findings
**Ollama**
- Setup: `ollama pull <model>`, `ollama serve` (port 11434); `hermes model` → "Custom endpoint (self-hosted / VLLM / etc.)" → URL `http://localhost:11434/v1` → skip API key → model name; config example adds `context_length: 64000` — [Providers: Ollama](https://hermes-agent.nousresearch.com/docs/integrations/providers#ollama--local-models-zero-config)
- Ollama "does **not** use your model's full context window by default": <24 GB VRAM → 4,096 tokens; 24–48 GB → 32,768; 48+ GB → 256,000 — [Providers: Ollama](https://hermes-agent.nousresearch.com/docs/integrations/providers#ollama--local-models-zero-config); same table in official Ollama docs, which add "agents, and coding tools should be set to at least 64000 tokens" — [Ollama docs: context-length](https://github.com/ollama/ollama/blob/main/docs/context-length.mdx)
- Ways to raise it: `OLLAMA_CONTEXT_LENGTH=64000 ollama serve`; systemd `Environment="OLLAMA_CONTEXT_LENGTH=64000"` via `sudo systemctl edit ollama.service`; or a Modelfile `FROM <model>` + `PARAMETER num_ctx 64000` then `ollama create <name>-64k -f Modelfile`; verify with `ollama ps` (CONTEXT column). "**You cannot set context length through the OpenAI-compatible API** (`/v1/chat/completions`)… This is the #1 source of confusion" — [Providers: Ollama](https://hermes-agent.nousresearch.com/docs/integrations/providers#ollama--local-models-zero-config)
- Conflict on default: the Ollama setup guide says "By default, Ollama uses a 2048-token context" — [Ollama guide](https://hermes-agent.nousresearch.com/docs/guides/local-ollama-setup#increase-ollamas-context-window); the providers page and Ollama's own docs give the VRAM-based 4K/32K/256K table — [Ollama docs](https://github.com/ollama/ollama/blob/main/docs/context-length.mdx)
- API key: "Leave empty or type `no-key` (Ollama doesn't need one)" — [Ollama guide: Step 3](https://hermes-agent.nousresearch.com/docs/guides/local-ollama-setup#step-3-configure-hermes)
- Keep-alive: Ollama unloads models after 5 min idle; set `OLLAMA_KEEP_ALIVE=24h` (systemd override) or `keep_alive: "24h"` per request — [Ollama guide: Step 6](https://hermes-agent.nousresearch.com/docs/guides/local-ollama-setup#keep-the-model-loaded)
- Ollama server knobs: `OLLAMA_NUM_PARALLEL` (default 1; RAM scales by `OLLAMA_NUM_PARALLEL * OLLAMA_CONTEXT_LENGTH`), `OLLAMA_FLASH_ATTENTION=1`, `OLLAMA_KV_CACHE_TYPE` (default `f16`; quantized K/V requires Flash Attention; global option), `OLLAMA_HOST` (binds 127.0.0.1:11434 by default), `OLLAMA_MODELS` (model dir) — [Ollama FAQ](https://github.com/ollama/ollama/blob/main/docs/faq.mdx)
- Hermes source: on a local endpoint it probes Ollama `/api/show` for the model's max window and **sends `extra_body.options.num_ctx` on every request** ("Ollama defaults num_ctx to 2048, so detect the max window and send num_ctx per request. model.ollama_num_ctx overrides; model.context_length caps the detected value (VRAM)") — [agent/agent_init_ollama.py](https://github.com/NousResearch/hermes-agent/blob/main/agent/agent_init_ollama.py), [custom provider: `extra_body["options"] = {"num_ctx": ollama_num_ctx}`](https://github.com/NousResearch/hermes-agent/blob/main/plugins/model-providers/custom/__init__.py)
- FAQ: if you set a custom `num_ctx` in Ollama, set the matching context length in Hermes — "Ollama's `/api/show` reports the model's *maximum* context, not the effective `num_ctx` you configured" — [FAQ](https://hermes-agent.nousresearch.com/docs/reference/faq#can-i-use-it-offline--with-local-models)
- Tool calling "is enabled by default — make sure your model supports it (check with `ollama show model-name`)" — [Providers: Troubleshooting](https://hermes-agent.nousresearch.com/docs/integrations/providers#tool-calls-appear-as-text-instead-of-executing)

**llama.cpp / llama-server**
- Docs command: `llama-server --jinja -fa -c 64000 -ngl 99 -m models/qwen2.5-coder-32b-instruct-Q4_K_M.gguf --port 8080 --host 0.0.0.0`; Hermes URL `http://localhost:8080/v1`; API key not needed; model name may be left blank to auto-detect if one model is loaded — [Providers: llama.cpp](https://hermes-agent.nousresearch.com/docs/integrations/providers#llamacpp--llama-server--cpu--metal-inference)
- "`--jinja` is required for tool calling. Without `--jinja`, llama-server ignores the `tools` parameter entirely" → raw JSON printed instead of a tool call. Verify via `http://localhost:8080/props` — `chat_template` field should be present — [Providers: llama.cpp](https://hermes-agent.nousresearch.com/docs/integrations/providers#llamacpp--llama-server--cpu--metal-inference)
- `-c`: recent builds default to `0` = GGUF training context, which "can OOM" for 128K+ models; set `-c` explicitly ≥64,000. With parallel slots `-np`, context is divided: `-c 64000 -np 4` gives 16K per slot, "below Hermes' minimum per active session" — [Providers: llama.cpp](https://hermes-agent.nousresearch.com/docs/integrations/providers#llamacpp--llama-server--cpu--metal-inference)
- Mac guide's llama-server line (applies to Linux too): `llama-server -m ~/models/Qwen3.5-9B-Q4_K_M.gguf -ngl 99 -c 131072 -np 1 -fa on --cache-type-k q4_0 --cache-type-v q4_0 --host 0.0.0.0`; KV cache for a 9B model at 128K: f16 ~16 GB, q8_0 ~8 GB, q4_0 ~4 GB; `curl -s http://localhost:8080/v1/models | jq '.data[].id'` gives the model name — [Mac guide](https://hermes-agent.nousresearch.com/docs/guides/local-llm-on-mac#start-the-server)
- llama.cpp native tool-call formats: Llama 3.1/3.3/3.2, Functionary v3.1/3.2, Hermes 2/3, Qwen 2.5, Qwen 2.5 Coder, Mistral Nemo, Firefunction v2, Command R7B, DeepSeek R1 ("WIP / seems reluctant to call any tools?"), GPT-OSS (Harmony); others use a Generic handler (`Chat format: Generic` in logs) that "may consume more tokens and be less efficient"; `--chat-template-file` overrides; parallel tool calls off by default (`"parallel_tool_calls": true` to enable) — [llama.cpp function-calling.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md)
- Hermes reads llama.cpp's actually-allocated `n_ctx` from `/v1/props` then `/props` (`default_generation_settings.n_ctx`), overriding `/v1/models` metadata — [agent/model_metadata.py](https://github.com/NousResearch/hermes-agent/blob/main/agent/model_metadata.py)
- Managed runtime: `local_runtime: {enabled: false, backend: auto|cuda|metal|vulkan|hip|cpu, detect_ports: [8081]}` (default probe `:8080` only). A self-run llama-server can be selected with `model.provider: llamacpp` by listing its port in `detect_ports` or with `providers: {llamacpp: {base_url: http://127.0.0.1:8081/v1, model: my-model}}`. Terminal path: `hermes model` → **Local models** installs a pinned engine, downloads a model, starts the server, sets it as default — [Local Models](https://hermes-agent.nousresearch.com/docs/user-guide/local-models#configuration)
- Endpoint test accepts the server root (`http://127.0.0.1:8080`) or the `/v1` URL and saves whichever served `/models` — [Local Models](https://hermes-agent.nousresearch.com/docs/user-guide/local-models#using-your-own-llama-server)

**vLLM**
- `vllm serve <model> --port 8000 --max-model-len 65536 --enable-auto-tool-choice --tool-call-parser hermes`; parsers listed: `hermes` (Qwen 2.5, Hermes 2/3), `llama3_json`, `mistral`, `deepseek_v3`, `deepseek_v31`, `xlam`, `pythonic`; `--max-model-len auto`, `--gpu-memory-utilization 0.95`, sizes like `64k` — [Providers: vLLM](https://hermes-agent.nousresearch.com/docs/integrations/providers#vllm--high-performance-gpu-inference)
- Qwen reasoning: if `--reasoning-parser qwen3` leaves `content` empty, disable the parser or pass `chat_template_kwargs.enable_thinking: false` via `extra_body` — [Providers: vLLM](https://hermes-agent.nousresearch.com/docs/integrations/providers#vllm--high-performance-gpu-inference)
- `--tool-call-parser qwen3_xml` plus a reasoning parser "can leak tool-call markup into plain text and return zero `tool_calls`" → use `model.streaming: false` — [Configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#disabling-api-streaming)

**SGLang**
- `python -m sglang.launch_server --model <m> --port 30000 --context-length 65536 --tool-call-parser qwen`; parsers `qwen`, `llama3`, `llama4`, `deepseekv3`, `mistral`, `glm`; `SGLANG_ALLOW_OVERWRITE_LONGER_CONTEXT_LEN=1` to exceed declared max; "SGLang defaults to 128 max output tokens" → configure `--default-max-tokens` server-side — [Providers: SGLang](https://hermes-agent.nousresearch.com/docs/integrations/providers#sglang--fast-serving-with-radixattention)

**LM Studio**
- `lms server start` (port 1234), `lms load qwen2.5-coder --context-length 64000` (`--estimate-only` to check fit); `hermes model` → "LM Studio" → Enter for `http://localhost:1234/v1`; `LM_API_KEY` if server auth on; `hermes config set model.lmstudio_load_mode jit|explicit`; tool calling since LM Studio 0.3.6 — [Providers: LM Studio](https://hermes-agent.nousresearch.com/docs/integrations/providers#lm-studio--desktop-app-with-local-models)

**Server-type auto-detection** (source): Hermes probes, in order, LM Studio `/api/v1/models`, Ollama `/api/tags` (body must contain `models`), llama.cpp `/v1/props`|`/props` (`default_generation_settings`), vLLM `/version`; skipped for known hosted providers — [agent/model_metadata.py `detect_local_server_type`](https://github.com/NousResearch/hermes-agent/blob/main/agent/model_metadata.py)

### Inferences
- On a CPU-only box, llama-server is the most controllable backend: explicit `-c`, `-np 1`, KV-cache quantization, `/props` that Hermes reads for the real window, and `--jinja` tool parsing. Ollama is easier but adds two risks (context defaults, and the open stream+tools hang in Q6).
- vLLM and SGLang are documented as GPU servers ("High-Performance GPU Inference"); they are not a realistic choice for a 4-core/15 GB/no-GPU container.
- Because Hermes sends `options.num_ctx` = the model's max from `/api/show` unless capped, an Ollama model advertising 128K–256K could be asked to allocate a huge KV cache on a 15 GB machine if Ollama honours that field on `/v1`. Always set `model.context_length` (caps auto-detected num_ctx) or `model.ollama_num_ctx: 65536` explicitly.

### Gaps
- Whether Ollama's OpenAI-compatible `/v1/chat/completions` actually honours `options.num_ctx` (Hermes docs say context "cannot" be set via `/v1`; Hermes source sends it anyway) was not verified against current Ollama.
- LM Studio headless (`lms`/daemon) on a Linux server without a desktop was not researched.

## 3. Minimum context window, how it is detected, how to override, and interaction with compression

### Takeaway
Hermes hard-refuses any model whose effective window is below **64,000 tokens** (`MINIMUM_CONTEXT_LENGTH = 64_000`), at startup, on model switches, for cron, and again at runtime when tools are attached; there is no supported switch to lower it (open feature request #53347, PR #116645 in progress). Context is resolved via a 9-step chain (config pin first; then per-provider model entry; cache; endpoint `/models`; …; 128K fallback), so for local servers set `model.context_length` to exactly what the server serves (and `-c`/`num_ctx` ≥ 64K). Compression is an LLM call that by default uses the main model, fires at 50% of the window, and its model must itself have ≥64K and ≥ the main model's window.

### Cited Findings
- "Sessions, model switches and cron jobs reject models below this (too little working memory). `MINIMUM_CONTEXT_LENGTH = 64_000`" — [agent/model_metadata.py](https://github.com/NousResearch/hermes-agent/blob/main/agent/model_metadata.py)
- Startup refusal text for a local endpoint: "Your local server is serving a N-token window. Start it with at least 64K context (llama.cpp: -c 64000; vLLM: --max-model-len; Ollama: OLLAMA_CONTEXT_LENGTH=64000 or a Modelfile num_ctx), or set model.ollama_num_ctx in config.yaml to the window it really serves (at least 64K)." Exception: provider `lmstudio` with an explicit positive `model.context_length` is allowed below the floor — [agent/agent_init.py `_enforce_minimum_context`](https://github.com/NousResearch/hermes-agent/blob/main/agent/agent_init.py)
- "Hermes Agent requires at least **64,000 tokens** of context for agent use with tools. Smaller windows are rejected at startup because the system prompt, tool schemas, and working conversation state need enough room" — [Providers: Ollama](https://hermes-agent.nousresearch.com/docs/integrations/providers#ollama--local-models-zero-config)
- `model.ollama_num_ctx` "is honoured on every local endpoint; only the automatic detection behind it uses Ollama's `/api/show`" — [Providers: Troubleshooting](https://hermes-agent.nousresearch.com/docs/integrations/providers#model-seems-to-forget-context-or-give-incoherent-responses)
- Second, runtime check: `_ollama_context_limit_error` in `agent/conversation_loop.py` checks the runtime `num_ctx` against the same 64K floor, but only when tools are attached; setting `context_length: 65536` while the server really runs 32K satisfies the startup check but not this one (user trace on v0.18.2) — [#53347 comment](https://github.com/NousResearch/hermes-agent/issues/53347)
- Feature request "Allow context_length below 64K — warn instead of hard failure" is open, labelled `needs-decision`; linked PR "feat(agent): allow explicit opt-in below the 64K context-length floor" (#116645); earlier PR #32770 proposed `allow_short_context` — [#53347](https://github.com/NousResearch/hermes-agent/issues/53347)
- Field data: a real Hermes request was ~23,855 input tokens "because the system prompt + tool schemas dominate the footprint" (Hermes 0.20.3 + LM Studio) — [#53347 comment](https://github.com/NousResearch/hermes-agent/issues/53347); contrast: docs say "Hermes's system prompt + tool schemas alone can use 4k–8k tokens" — [Providers: Troubleshooting](https://hermes-agent.nousresearch.com/docs/integrations/providers#model-seems-to-forget-context-or-give-incoherent-responses)
- Resolution chain: (1) `model.context_length` (a "pin", labelled `(pinned)`, dropped automatically when you switch model/provider/base URL), (2) `providers.<name>.models.<id>.context_length`, (3) persistent cache, (4) endpoint `/models`, (5) Anthropic `/v1/models`, (6) OpenRouter API, (7) Nous Portal, (8) models.dev, (9) fallback defaults (128K) — [Providers: Context Length Detection](https://hermes-agent.nousresearch.com/docs/integrations/providers#context-length-detection)
- `hermes model` prompts for context length on a custom endpoint (blank = auto-detect). Set it manually when Ollama `num_ctx` < model max, to limit below max to save memory, or behind a proxy without `/v1/models` — [Providers: Context Length Detection](https://hermes-agent.nousresearch.com/docs/integrations/providers#context-length-detection)
- "Context limit: 2048 tokens" at startup = server reported a low/no value; fix with explicit `context_length: 64000`. Check with the startup line "Context limit: X tokens", `ollama ps`, `curl http://localhost:8080/props | jq '.default_generation_settings.n_ctx'`, vLLM `--max-model-len` — [Providers: Troubleshooting](https://hermes-agent.nousresearch.com/docs/integrations/providers#context-limit-2048-tokens-at-startup)
- If the configured window is larger than the server's `-c`, llama.cpp silently truncates (`stop processing: n_tokens = 65535, truncated = 1`); Hermes re-measures and compacts, else ends with "Context length exceeded: compression could not reduce the rebuilt request below the safe threshold" — fix by matching `context_length` to server `-c` — [FAQ](https://hermes-agent.nousresearch.com/docs/reference/faq#context-length-exceeded)
- Compression block: `compression.enabled: true`, `threshold: 0.50`, `threshold_tokens: null`, `target_ratio: 0.20`, `tail_mode: lean` (tail clamped 10K–25K, never >20% of window), `protect_last_n: 20`, `protect_first_n: 3`, `context_timeout_seconds: 120`, `context_total_ceiling_seconds: 600`, `proactive_prune_tokens: 0` (try 48000 for no-LLM pruning of old tool output); summarizer configured under `auxiliary.compression` (`model: ""` = main model, `provider: "auto"`, `base_url`) — [Configuration: Context Compression](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#context-compression)
- "The summary model **must** have a context window at least as large as your main agent model's… if [smaller]… the middle turns are **dropped without a summary**" — [Configuration: Context Compression](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#context-compression); source also requires the aux compression model to meet the 64K floor ("Aux model must meet MINIMUM_CONTEXT_LENGTH like the main model") — [code search: agent/conversation_compression.py](https://github.com/NousResearch/hermes-agent/blob/main/agent/conversation_compression.py)
- Time a llama.cpp server spends reading the prompt does not count toward compression ceilings; server-reported prompt progress pushes deadlines back — [Configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#context-compression)
- Compressor window is clamped to the effective Ollama `num_ctx` so the trigger fires below the served window — [agent/agent_init_ollama.py](https://github.com/NousResearch/hermes-agent/blob/main/agent/agent_init_ollama.py)
- Legacy `compression.summary_model/summary_provider/summary_base_url` auto-migrate to `auxiliary.compression.*` (config v17) — [Configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#context-compression)
- Local runtime: "Every recommended model gets at least a 64K context window"; context starts at what fits and grows ("Context window grown"), compressing instead if it cannot grow — [Local Models](https://hermes-agent.nousresearch.com/docs/user-guide/local-models#how-memory-management-works)

### Inferences
- With a 64K window and default `threshold: 0.50`, compression fires around ~32K tokens; if the fixed prompt is really ~24K tokens (field report), only ~8K tokens of conversation remain before every turn triggers a compression LLM call — very expensive on CPU. Reduce the fixed prompt (Q6) and/or raise the server window to 96K–128K if RAM allows (Qwen3.5-9B with q4/q8 KV makes this feasible).
- Never "lie" with `context_length: 65536` over a 32K server: it passes startup but fails the runtime tool-attached check and/or causes silent truncation.
- Pin `model.context_length` explicitly for local servers; it also removes any dependence on models.dev/OpenRouter metadata lookups (outbound network) for context detection.

### Gaps
- Exact current token size of Hermes' system prompt + default tool schemas (docs say 4–8K; a user measured ~24K with their toolset). `hermes prompt-size` reports it, but no published number for defaults.
- Merge status/semantics of PR #116645 (opt-in below 64K) as of v0.23.0 unknown.

## 4. Recommended models, and what is realistic on 4 CPU cores / 15 GB RAM / no GPU

### Takeaway
Hermes docs recommend Qwen3.5-9B (Q4_K_M GGUF, 5.3 GB) as the starter local model and gemma4:31b for "best quality" via Ollama (needs 24+ GB, too big here); Hermes' own code warns that Nous **Hermes 3/4 models are NOT agentic** for Hermes Agent, contradicting third-party guides that recommend Hermes 4.x. On 4 CPU cores and 15 GB RAM, the realistic envelope is a ~4–9B Qwen3.5/Qwen3-class model at Q4_K_M with a quantized KV cache at 64K context, accepting a slow (possibly multi-minute) first-turn prefill and low single-digit-to-~5 tok/s generation.

### Cited Findings
- "For getting started, we recommend **Qwen3.5-9B**… fits comfortably in 8GB+ of unified memory with quantization"; `Qwen3.5-9B-Q4_K_M` 5.3 GB on disk, ~10 GB RAM at 128K with quantized KV cache; "The 9B is the sweet spot for 8-16 GB machines"; download `huggingface-cli download unsloth/Qwen3.5-9B-GGUF Qwen3.5-9B-Q4_K_M.gguf --local-dir ~/models` — [Mac guide](https://hermes-agent.nousresearch.com/docs/guides/local-llm-on-mac#choosing-a-model)
- Ollama guide model table: `gemma4:31b` ~20 GB / 24+ GB RAM / tool calling yes; `gemma2:27b`, `gemma2:9b`, `llama3.2:3b` = no tool calling; "of the models listed above, only `gemma4:31b` has reliable tool calling" — [Ollama guide](https://hermes-agent.nousresearch.com/docs/guides/local-ollama-setup#step-2-pull-a-model)
- CPU expectations: "A 9B model on a modern 8-core CPU gives ~10 tokens/sec. A 31B model on CPU is slower (~2–5 tokens/sec) — each response takes 30–120 seconds"; minimum spec 8 GB RAM (3B models), 4 cores; GPU "Not required" — [Ollama guide: What You Need](https://hermes-agent.nousresearch.com/docs/guides/local-ollama-setup#what-you-need)
- "What works well locally: File editing and code generation — models 9B+ handle this well"; "Very complex multi-step reasoning — 70B+ or cloud models… are noticeably better" — [Ollama guide](https://hermes-agent.nousresearch.com/docs/guides/local-ollama-setup#what-works-well-locally)
- Hermes code: "Nous Research Hermes 3 & 4 models are NOT agentic and are not designed for use with Hermes Agent. They lack the tool-calling capabilities required for agent workflows. Consider using an agentic model instead (Claude, GPT, Gemini, DeepSeek, etc.)"; regex matches e.g. `NousResearch/Hermes-3-Llama-3.1-70B`, `hermes-4-405b`, `hermes3:70b` (not `qwen3:14b`) — [hermes_cli/model_switch.py](https://github.com/NousResearch/hermes-agent/blob/main/hermes_cli/model_switch.py); a non-CLI surface shows "⚠ … Consider an agentic model instead (Claude, GPT, Gemini, Qwen-Coder, etc.)" — [agent/agent_init.py](https://github.com/NousResearch/hermes-agent/blob/main/agent/agent_init.py)
- Contradicting third-party claim: "the best Ollama model is Hermes 4.3 36B… if you have a 24 GB GPU — and Qwen3 14B (~9.3 GB) is the best pick for a single 12-16 GB card" — [localaimaster.com](https://localaimaster.com/blog/hermes-agent-ollama) (secondary, conflicts with Hermes source)
- Hermes-4-14B on Hugging Face has only 40,960 context out of the box (below the floor); a user hit the floor with qwen3-8b (max 32,768) — [#53347 comments](https://github.com/NousResearch/hermes-agent/issues/53347)
- Ollama-packaged `qwen2.5:7b/14b/32b` are reported hard-capped at 32,768 context in the GGUF; `ollama ps` stays 32,768 regardless of `OLLAMA_CONTEXT_LENGTH`/`num_ctx`; `mistral-small:22b`, `llama3.3:70b`, `llama3.1:8b` reported working at 128K — [#25629](https://github.com/NousResearch/hermes-agent/issues/25629) (user report)
- Forcing `num_ctx` 65536 on Qwen2.5-7B (native 32K) "has a real quality cost past ~32K" — [#53347 comment](https://github.com/NousResearch/hermes-agent/issues/53347)
- User story on the Hermes site: "Fairly good with qwen3.5-4b, very decent with qwen3.5-9b, VERY good with 27b. Personal agent? Yes. Coding for high complexity tasks? Not really…" — [website/src/data/userStories.json](https://github.com/NousResearch/hermes-agent/blob/main/website/src/data/userStories.json)
- Tool-use enforcement (system-prompt nudges to actually call tools) is auto-enabled for model names containing `gpt`, `codex`, `gemini`, `gemma`, `grok`, `glm`, `qwen`, `deepseek`, `muse`; set `agent.tool_use_enforcement: true` or a substring list for others (e.g. `llama`) — [Configuration: Tool-Use Enforcement](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#tool-use-enforcement)
- llama.cpp has native tool-call handlers for Qwen 2.5 / Hermes 2/3 / Llama 3.x / Mistral Nemo / GPT-OSS; others fall to the Generic handler — [llama.cpp function-calling.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md)
- Managed runtime recommends "the highest-quality model that runs entirely in GPU or unified memory at a predicted 20 tokens per second or more… When no model reaches the floor, Hermes recommends none, and you can still choose any model that fits"; never offers builds below 4-bit — [Local Models](https://hermes-agent.nousresearch.com/docs/user-guide/local-models#how-hermes-picks-what-to-download)
- 9B at 128K: KV f16 ~16 GB, q8_0 ~8 GB, q4_0 ~4 GB — [Mac guide](https://hermes-agent.nousresearch.com/docs/guides/local-llm-on-mac#memory-optimization-for-constrained-systems)

### Inferences
- Best fit for this box: **Qwen3.5-9B-Q4_K_M** (≈5.3 GB weights) on llama-server with `-c 65536` and q8_0 (or q4_0) KV cache: by the Mac-guide numbers, 64K context ≈ half of the 128K figures, i.e. ≈4 GB (q8_0) / ≈2 GB (q4_0) KV, total ≈7.5–9.5 GB, leaving headroom in 15 GB. **Qwen3.5-4B** is the fallback if latency is unacceptable (user story: "fairly good"). These are the only family explicitly endorsed by Hermes docs/users at this size.
- Qwen3-8B / Qwen2.5-7B are risky: native 32K windows fail the 64K floor unless RoPE/YaRN scaling is enabled, with quality loss beyond the trained window.
- gpt-oss-20b (MXFP4 ≈13 GB file) and 27–35B models will not fit comfortably in 15 GB RAM alongside a 64K KV cache; gemma4:31b (24+ GB) is out.
- Throughput estimate (not measured): the docs' "~10 tok/s for 9B on 8 cores" implies roughly ~4–6 tok/s generation on 4 cores. Prompt processing on 4 cores is far slower than on GPU; a first turn with a ~10–24K-token fixed prompt could take several to 15+ minutes. llama-server's prompt caching means later turns only process new tokens, provided only one slot (`-np 1`) is used and the prefix stays stable.
- Avoid Nous Hermes 3/4 checkpoints as the main agent model despite the naming; Hermes Agent itself flags them.

### Gaps
- No official benchmark of Hermes Agent tool-call success rates per local model was found; recommendations are qualitative.
- No measured tok/s for 4-core CPUs; the Qwen3.5 small-model architecture's exact KV footprint at 64K was not independently verified (numbers above are scaled from the Mac guide).
- Exact llama.cpp flags for YaRN-extending Qwen3-8B to 64K+ were not sourced in this research.

## 5. Auxiliary model slots and how to keep them local (no silent paid-cloud calls)

### Takeaway
Side tasks (vision/screenshot analysis, compression summaries, session titles, dangerous-command approval classifier, MCP dispatch, TTS audio tags, voice chat, kanban triage/decomposer, profile describer, curator, background memory/skill review, MoA, delegation subagents) all call an LLM; with `provider: "auto"` they now route to the **main model**, so a local main model keeps them local by default. Web extraction no longer uses an auxiliary LLM. To be safe, pin the important slots to `provider: main` (or an explicit `base_url`), disable title generation if desired, avoid `provider: openai` without a `base_url`, and don't define cloud fallbacks or cloud API keys.

### Cited Findings
- "By default (`auxiliary.*.provider: "auto"`), Hermes routes every auxiliary task to your **main chat model**"; earlier builds split aggregator users (OpenRouter/Nous) onto a cheap provider-side default; "`auto` now uses the main model for everyone" — [Configuration: Auxiliary Models](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#auxiliary-models)
- Contradiction on vision: the Provider Options table still says `"auto"` = "Best available (default). Vision tries OpenRouter → Nous → Codex." — [Configuration: Provider Options](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#provider-options)
- Interactive picker (`hermes model` → "Configure auxiliary models") lists slots: `vision`, `title_generation`, `tts_audio_tags`, `voice_chat`, `compression`, `approval`, `triage_specifier`, `kanban_decomposer`, `profile_describer`, `delegation` (writes top-level `delegation.provider/model`; `auto` = inherit parent) — [Configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#configuring-auxiliary-models-interactively)
- Universal per-slot knobs: `provider`, `model`, `base_url` (overrides provider), `api_key`, `timeout`, `reasoning_effort` (`none`…`max`). `"main"` = "use whatever provider my main agent uses" (valid only inside `auxiliary:`, `compression:`, fallback entries — not for `model.provider`) — [Configuration: universal config pattern](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#the-universal-config-pattern)
- Local servers can be named directly in aux slots: `provider: ollama` (also `vllm`, `llamacpp`, `llama.cpp`) with `base_url: http://127.0.0.1:11434` and empty `api_key` "routes through the custom endpoint with a placeholder key, and a bare `host:port` base_url gets the `/v1` suffix automatically" — [Configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#the-universal-config-pattern)
- Footgun: `provider: openai` routes to the block's `base_url`, else `OPENAI_BASE_URL`, else `https://api.openai.com/v1` with `OPENAI_API_KEY` — "removing `base_url` while keeping `provider: openai` moves that task to the public OpenAI endpoint" — [Configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#the-universal-config-pattern)
- For direct `base_url` aux endpoints Hermes uses the slot's `api_key` or `OPENAI_API_KEY`, never `OPENROUTER_API_KEY`; with neither, the main key is reused only if `base_url` has the main endpoint's exact origin — [Configuration: Common Setups](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#common-setups)
- Unresolvable aux blocks fall back to the main model with a warning; `hermes doctor` reports failing `auxiliary.<task>` blocks; `hermes config` shows overrides — [Configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#the-universal-config-pattern)
- Local vision example: `auxiliary: {vision: {provider: "main", model: "my-local-model"}}` — "Vision requires a multimodal model"; or `model.supports_vision: true` to send images natively from a custom model — [Configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#common-setups), [Providers](https://hermes-agent.nousresearch.com/docs/integrations/providers#named-custom-providers)
- Title generation: `auxiliary.title_generation.enabled: false` disables; `model_upgrade_enabled: false` keeps the instant derived title with no model call. On a `custom` main provider (llama.cpp, Ollama, vLLM, LM Studio), the title call is sent **after** the reply, because a single-slot server could otherwise answer the reply with `{"title": ...}` — [Configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#configuring-auxiliary-models-interactively)
- Aux default timeouts: vision 120s, approval 30s, compression 120s, title 30s, others 30s; "Increase these if you use slow local models for auxiliary tasks" — [Configuration: Full auxiliary config reference](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#full-auxiliary-config-reference)
- Each aux task may have a `fallback_chain`; if all fail "Hermes falls back to the main agent model as a final safety net" — [Configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#per-task-fallback-chain-for-auxiliary-tasks)
- "`AUXILIARY_WEB_EXTRACT_*` variables are obsolete — web extraction no longer uses an auxiliary LLM"; long pages are truncated deterministically — [Configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#environment-variables-legacy), [Env vars](https://hermes-agent.nousresearch.com/docs/reference/environment-variables)
- Legacy env vars still exist for vision only: `AUXILIARY_VISION_PROVIDER/MODEL/BASE_URL/API_KEY` — [Env vars](https://hermes-agent.nousresearch.com/docs/reference/environment-variables)
- Background memory review ("thread=bg-review") runs on the main model and on single-slot local servers can occupy the server's context, producing "The model server rejected this request as too large, but this conversation is only about N tokens…" — wait and `/retry` — [FAQ](https://hermes-agent.nousresearch.com/docs/reference/faq#context-length-exceeded); a same-model review fork inherits the parent's reasoning effort — [Configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#the-universal-config-pattern)
- Source: memory review cadence `memory.nudge_interval` (default 10) and skill-creation cadence `skills.creation_nudge_interval` (default 10); the check only fires when the interval is > 0 — [agent/agent_init.py](https://github.com/NousResearch/hermes-agent/blob/main/agent/agent_init.py), [code search: agent/turn_context.py](https://github.com/NousResearch/hermes-agent/blob/main/agent/turn_context.py)
- Built-in memory is char-limited text (`memory.memory_char_limit: 2200`, `user_char_limit: 1375`), configured under `memory:`; cloud memory providers (Honcho `HONCHO_API_KEY`, Supermemory `SUPERMEMORY_API_KEY`) are optional keys — [Configuration: Memory](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#memory-configuration), [Providers: Optional API Keys](https://hermes-agent.nousresearch.com/docs/integrations/providers#optional-api-keys)
- Other features that call external (paid) services only when keys are set: Firecrawl web scraping, Browserbase, FAL image gen, ElevenLabs/OpenAI/Mistral TTS & STT — [Providers: Optional API Keys](https://hermes-agent.nousresearch.com/docs/integrations/providers#optional-api-keys)

### Inferences
- Recommended local-only aux block:
  ```yaml
  auxiliary:
    compression:      {provider: main, timeout: 900, no_progress_timeout: 600}
    vision:           {provider: main}          # only useful if the model is multimodal
    title_generation: {enabled: false}          # or model_upgrade_enabled: false
    approval:         {provider: main, timeout: 300}
  ```
  plus no `fallback_providers`, and no `OPENROUTER_API_KEY` / `OPENAI_API_KEY` / `NOUS` OAuth in `~/.hermes/.env` so that even a mis-routed slot has no cloud credential to use. Verify with `hermes doctor` and `hermes config`.
- On a single-slot CPU server every aux call (titles, memory/skill reviews, approval classifier, compression) competes with the main turn; consider raising `memory.nudge_interval` / `skills.creation_nudge_interval` (or 0 if that disables them — inferred from the `> 0` check, not documented) to cut background load.
- Since the aux compression model must have ≥64K context and ≥ the main window, pointing compression at a *smaller* local model is not an option; use `main`.

### Gaps
- No embedding model slot was found in the core configuration docs; one doc passage lists "embedding" among auxiliary tasks that use `key_cmd` credentials ([Providers](https://hermes-agent.nousresearch.com/docs/integrations/providers#command-minted-credentials-key_cmd)), but which feature calls it and how to route it was not found.
- Whether `memory.nudge_interval: 0` cleanly disables background review is inferred from source, not documented.
- The vision "auto" contradiction (main model vs OpenRouter→Nous→Codex chain) was not resolved in source.

## 6. Known pitfalls with local backends and their fixes (incl. timeouts for slow CPUs)

### Takeaway
The recurring failures are: (a) tool calls printed as text because the server's tool parsing is off (`--jinja`, vLLM/SGLang parser flags); (b) context below 64K or mismatched with the server; (c) Ollama hanging on `stream=true` + tools (open issue #25629); (d) very long silent prefill on CPU being mistaken for a hang; (e) reasoning/thinking routing leaving `content` empty; (f) single-slot contention from background calls. Hermes auto-relaxes timeouts for local endpoints (read 1800s, stale-stream 900s ceiling), but slow 4-core CPUs may still need higher `HERMES_LOCAL_STREAM_STALE_TIMEOUT` and larger aux timeouts.

### Cited Findings
- Tool calls as text — fixes: llama.cpp add `--jinja`; vLLM `--enable-auto-tool-choice --tool-call-parser hermes`; SGLang `--tool-call-parser qwen`; Ollama ensure model supports tools (`ollama show`); LM Studio ≥0.3.6 with a native-tool model — [Providers: Troubleshooting](https://hermes-agent.nousresearch.com/docs/integrations/providers#tool-calls-appear-as-text-instead-of-executing)
- Ollama stream+tools hang (open, P2, label `area/local-models`): Hermes v0.13.0 + Ollama v0.23.2, CPU-only: `stream=false`+25 tools OK (~12s), `stream=true`+3 tools hangs with 0 bytes, `stream=true`+25 tools → HTTP 500 after 1m17s, and the whole Ollama API becomes unresponsive until restart. A second user on Hermes 0.16.0 reproduced with just 1 tool (qwen2.5 64k variant); Ollama streams the whole tool call in one chunk then a final chunk with `finish_reason: "tool_calls"` and no data. `api_mode: chat_completions` and `skip_provider_detection: true` did not help. Linked fix PR #25638 "skip local num_ctx probe for explicit chat completions". The same issue reported Hermes' pre-flight probes (`/api/v1/models`, `/api/tags`, `/api/show`, `/v1/props`, `/props`, `/version`) aborting when routed via a LiteLLM proxy that 404s them — [#25629](https://github.com/NousResearch/hermes-agent/issues/25629)
- Issue #25629 states "Hermes Agent sends `stream=True` for all LLM calls" (at v0.13.0); current docs add `model.streaming: false` to force non-streaming for the whole session — [#25629](https://github.com/NousResearch/hermes-agent/issues/25629), [Configuration: Disabling API streaming](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#disabling-api-streaming)
- Slow first response (prefill): Hermes sends system prompt + all enabled tool schemas every call; on CPU "the model can sit silent for minutes… This is expected behaviour, not a hang". Mitigations: keep model loaded (`OLLAMA_KEEP_ALIVE=24h`), `HERMES_API_TIMEOUT=1800` in `~/.hermes/.env` (env var, "not a `config.yaml` key"), **`hermes prompt-size`** for a byte breakdown, trim toolsets with `hermes tools`, uninstall unused skills with `hermes skills`; use `/compress` regularly — [Ollama guide](https://hermes-agent.nousresearch.com/docs/guides/local-ollama-setup#slow-first-response-prefill)
- Timeout table: socket read 120s → auto 1800s for local (`HERMES_STREAM_READ_TIMEOUT`); stale stream 180s → 900s ceiling for local (`agent.local_stream_stale_timeout` / `HERMES_LOCAL_STREAM_STALE_TIMEOUT`, base `HERMES_STREAM_STALE_TIMEOUT`); stale non-stream 90s → auto-disabled for local when implicit (`providers.<id>.stale_timeout_seconds` / `HERMES_API_CALL_STALE_TIMEOUT`); Responses first-event watchdog 120s → 900s for local (`HERMES_CODEX_TTFB_TIMEOUT_SECONDS`); non-streaming API call 1800s (`providers.<id>.request_timeout_seconds`/`timeout_seconds` or `HERMES_API_TIMEOUT`); opt-in `agent.stream_max_lifetime` — [Configuration: API Timeouts](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#api-timeouts)
- Provider-level timeouts `providers.<id>.request_timeout_seconds` and `providers.<id>.models.<model>.timeout_seconds` win over `HERMES_API_TIMEOUT` — [Configuration: Provider Timeouts](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#provider-timeouts)
- Version drift: older pages/FAQ say stale-stream detection is "Disabled entirely" for local — [Mac guide](https://hermes-agent.nousresearch.com/docs/guides/local-llm-on-mac#timeouts), [FAQ](https://hermes-agent.nousresearch.com/docs/reference/faq); env-var reference says the 900s finite ceiling "replaces the former infinite disable" — [Env vars](https://hermes-agent.nousresearch.com/docs/reference/environment-variables); `HERMES_STREAM_STALE_GIVEUP` (default 5) aborts after consecutive stale kills — [Env vars](https://hermes-agent.nousresearch.com/docs/reference/environment-variables)
- Local endpoint detection (which triggers these auto-bumps): loopback (`localhost`, `127.0.0.1`, `::1`, `0.0.0.0`), unqualified hostnames (Docker Compose service names), `*.local`, RFC-1918, link-local, Tailscale CGNAT 100.64/10 — [agent/model_metadata.py `is_local_endpoint`](https://github.com/NousResearch/hermes-agent/blob/main/agent/model_metadata.py)
- Compression timeouts for slow summarizers: `compression.context_timeout_seconds` (120, floored at `auxiliary.compression.timeout`, min 300s), `context_total_ceiling_seconds` (600), gateway `hygiene_timeout_seconds` (30), `hygiene_total_ceiling_seconds` (600); `auxiliary.compression.no_progress_timeout` default 60s ("Raising `timeout` alone does **not** widen the progress window") — [Configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#stream-progress-timeout)
- Truncated responses: low server output default (SGLang 128 tokens → `--default-max-tokens`); Hermes has no output-cap setting — [Providers](https://hermes-agent.nousresearch.com/docs/integrations/providers#responses-get-cut-off-mid-sentence)
- Reasoning/thinking: vLLM `--reasoning-parser qwen3` can leave `content` empty → disable parser or `extra_body.chat_template_kwargs.enable_thinking: false` — [Providers: vLLM](https://hermes-agent.nousresearch.com/docs/integrations/providers#vllm--high-performance-gpu-inference); Hermes preserves `reasoning`/`reasoning_content` as trace data, not as the answer — same source
- Single-slot contention ("rejected this request as too large, but this conversation is only about N tokens") — usually a background memory review; wait and `/retry`, or fix server window — [FAQ](https://hermes-agent.nousresearch.com/docs/reference/faq#context-length-exceeded)
- Related issue titles (bodies not read): "#91373 `include_usage` makes the final chunk usage-only (no `finish_reason`)… hermes misreads spec-compliant vLLM streams as network cuts" (closed Aug 2026); "#56004 Thinking models lose their own reasoning between tool calls and turns on OpenAI-compatible endpoints" (closed Jul 2026); "#6626 Gemma 4 tool calling support (parser availability & required configuration)" (open); "#4505 Optimize Ollama Integration: Native /api/chat vs OpenAI-Compatible Endpoint" (closed) — [GitHub issue search](https://github.com/NousResearch/hermes-agent/issues?q=is%3Aissue+ollama)
- Third-party report title: "Hermes Agent v0.11.0 in Docker against a remote llama.cpp server… Some API calls fail with HTTP…" — [Reddit r/LocalLLM](https://www.reddit.com/r/LocalLLM/comments/1sxhtu0/hermes_agent_not_working_with_local_llamacpp/) (snippet only)
- WSL2 NAT: `localhost` doesn't reach a Windows-hosted server; use mirrored networking or host IP and bind the server to `0.0.0.0` — [Providers: WSL2](https://hermes-agent.nousresearch.com/docs/integrations/providers#wsl2-networking-windows-users)

### Inferences
- For the 4-core CPU container, put in `~/.hermes/.env`: `HERMES_LOCAL_STREAM_STALE_TIMEOUT=3600` and `HERMES_STREAM_READ_TIMEOUT=3600` (prefill of a 10–24K-token prompt at CPU speeds can exceed the 900s stale ceiling), keep `HERMES_API_TIMEOUT=1800`+; and raise `auxiliary.*.timeout` (title/approval 30s defaults are far too short for CPU).
- Given #25629 is still open, prefer llama-server over Ollama on CPU; if Ollama is used and a tool turn hangs, try `model.streaming: false` (newer escape hatch not tested by the issue reporters).
- Trim the fixed prompt aggressively (`hermes prompt-size`, `hermes tools` to disable unused toolsets such as browser/image/TTS) — this is the biggest lever for CPU latency and for staying under the compression threshold.
- Use `-np 1` on llama-server (and `OLLAMA_NUM_PARALLEL=1`) so the whole window is available to one session and prompt-cache reuse works.

### Gaps
- Whether #25629 is fixed by v0.23.0 or by a newer Ollama release is unknown (issue still open, last activity Sep 2026).
- No documented behaviour for llama-server's `--reasoning-format` / Qwen3.5 thinking with Hermes; `agent.reasoning_effort: none` is the documented Hermes-side knob.

## 7. Installing and running Ollama and/or llama.cpp server on a headless Linux box without GPU; download hosts

### Takeaway
Ollama installs via `curl -fsSL https://ollama.com/install.sh | sh` (or the `ollama-linux-amd64.tar.zst` tarball) — both redirect to GitHub release assets — and pulls models from `registry.ollama.ai` with blobs served from a Cloudflare R2 bucket. llama.cpp models come from Hugging Face (`huggingface.co` → `us.aws.cdn.hf.co` Xet CDN). From this target container all of those download paths worked, PyPI/npm are reachable (proxy no-proxy list), while `cdn-lfs.huggingface.co` is refused by the proxy (not needed for current HF downloads).

### Cited Findings
- Ollama Linux install: `curl -fsSL https://ollama.com/install.sh | sh`; manual: `curl -fsSL https://ollama.com/download/ollama-linux-amd64.tar.zst | sudo tar x -C /usr` then `ollama serve`; optional systemd unit with `ExecStart=/usr/bin/ollama serve`, `Restart=always`; `sudo systemctl daemon-reload && sudo systemctl enable ollama` — [Ollama docs: linux.mdx](https://github.com/ollama/ollama/blob/main/docs/linux.mdx); Hermes guide: verify with `ollama --version` and `curl http://localhost:11434/api/tags` → `{"models":[]}` — [Ollama guide: Step 1](https://hermes-agent.nousresearch.com/docs/guides/local-ollama-setup#step-1-install-ollama)
- Ollama behind a proxy: "Use `HTTPS_PROXY`… Ensure the proxy certificate is installed as a system certificate"; "Avoid setting `HTTP_PROXY`. Ollama does not use HTTP for model pulls, only HTTPS. Setting `HTTP_PROXY` may interrupt client connections to the server" — [Ollama FAQ](https://github.com/ollama/ollama/blob/main/docs/faq.mdx)
- Model test call: `curl http://localhost:11434/v1/chat/completions -H "Content-Type: application/json" -d '{"model": "...", "messages": [{"role":"user","content":"Say hello"}], "max_tokens": 50}'` — [Ollama guide: Step 2](https://hermes-agent.nousresearch.com/docs/guides/local-ollama-setup#step-2-pull-a-model)
- llama.cpp: build with `cmake -B build && cmake --build build --config Release` → `./build/bin/llama-server`; GGUFs "from Hugging Face… Q4_K_M quantization offers the best balance" — [Providers: llama.cpp](https://hermes-agent.nousresearch.com/docs/integrations/providers#llamacpp--llama-server--cpu--metal-inference); `huggingface-cli download unsloth/Qwen3.5-9B-GGUF Qwen3.5-9B-Q4_K_M.gguf --local-dir ~/models`; gated models need `huggingface-cli login` — [Mac guide](https://hermes-agent.nousresearch.com/docs/guides/local-llm-on-mac#download-the-model)
- Managed runtime (`hermes model` → Local models, `local_runtime.backend: cpu`) downloads engine components "from the URLs and SHA-256 pins in `pm/lock.json`", supports Linux CPU builds, resumes partial downloads; "Engine versions come only from PM's lockfile" — [Local Models](https://hermes-agent.nousresearch.com/docs/user-guide/local-models#requirements-and-limits)
- Hermes installer one-liner (for reference): `curl -fsSL https://raw.githubusercontent.com/NousResearch/hermes-agent/main/scripts/install.sh | bash` — [localaimaster.com](https://localaimaster.com/blog/hermes-agent-ollama) (secondary)

### Inferences
- Direct observation from this research container on 2026-11-08 (curl probes, not a published source):
  - `https://ollama.com/install.sh` → 307 → `github.com/ollama/ollama/releases/latest/download/install.sh` → `release-assets.githubusercontent.com` — download succeeded (206). Same redirect for `ollama-linux-amd64.tar.zst`.
  - `https://registry.ollama.ai/v2/library/qwen3/manifests/8b` → 200; blob download redirects to `dd20bb891979d25aebc8bec07b2b3bbc.r2.cloudflarestorage.com` → 206 (works), so `ollama pull` should work through the proxy (needs `HTTPS_PROXY` + the proxy CA in the system store).
  - `https://huggingface.co/Qwen/Qwen3-8B-GGUF/resolve/main/Qwen3-8B-Q4_K_M.gguf` → redirect to `us.aws.cdn.hf.co/xet-bridge-us/...` → 206 (works). `cdn-lfs.huggingface.co` CONNECT is refused by the proxy (policy denial) — irrelevant for Xet-backed repos but could matter for older LFS-only repos.
  - `github.com/<owner>/<repo>/releases/latest` HTML page returns 403 via the proxy, but `/releases/latest/download/<asset>` redirects work; the llama.cpp asset name guessed (`llama-b6000-bin-ubuntu-x64.zip`) 404'd under tag `v0.9.0`, so the current llama.cpp Linux CPU asset name must be discovered (e.g. via `git ls-remote --tags` which works, or by building from source with `git clone` + `cmake`).
  - PyPI, files.pythonhosted.org and registry.npmjs.org are in the proxy's no-proxy list and reachable: `pip install llama-cpp-python[server]` (source build; CPU wheel index at `abetlen.github.io/llama-cpp-python/whl/cpu/` also reachable) and npm `node-llama-cpp` 3.22.3 with prebuilt `@node-llama-cpp/linux-x64` are fallback ways to get a llama.cpp server binary.
  - The proxy no-proxy list includes `localhost,127.0.0.1,::1`, so Hermes → local server traffic bypasses the HTTPS proxy.
